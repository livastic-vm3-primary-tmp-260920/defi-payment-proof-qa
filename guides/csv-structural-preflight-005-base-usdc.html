Runnable payment-handshake preflight

This exact example uses invented .invalid email addresses. It does not send a payment signature. If the request body is valid, the service returns HTTP 402 Payment Required; the response includes the payment terms to be accepted by your own authorized x402 client. Running the command alone cannot buy the report.

curl -i --request POST \
  'https://vm5-openapi-x402.onrender.com/v1/csv-preflight' \
  --header 'Content-Type: application/json' \
  --data '{"csvText":"email,amount,date,note\na@example.invalid,12.5,2026-10-20,paid\na@example.invalid,12.5,2026-10-20,paid\nb@example.invalid,not-a-number,2026-13-99,=1+1","expectedColumns":["email","amount","date","note"]}'

Fresh read-only smoke evidence on 20 October 2026: the example was accepted for payment negotiation (HTTP 402 with PAYMENT-REQUIRED), while an empty CSV was rejected HTTP 400 without a payment challenge. Those responses show billing is gated; neither proves a successful paid delivery.

Scope and operating limits

  • UTF-8 JSON body; CSV text at most 32 KiB; at most 500 data rows and 40 columns.
  • Optional expected column names can make missing or reordered fields easier to spot.
  • Paid results report structure and issue locations rather than raw source rows. Infrastructure-level request logging may still apply; do not send passwords, wallet seeds or confidential customer records.
  • The service flags patterns; it cannot certify database integrity, privacy-law compliance, merchant identity, or production data safety.
  • Network: eip155:8453; asset: native Circle USDC on Base. Only the buyer's own wallet authorizes payment.
